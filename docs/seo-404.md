# Unknown URLs return 200, and why that is a server change

## The symptom

Every path on the site returns `200 OK` with the SPA shell, including paths
that render the 404 page:

```
$ curl -s -o /dev/null -w "%{http_code}\n" https://shikshacom.com/this-does-not-exist
200
$ curl -s -o /dev/null -w "%{http_code}\n" https://shikshacom.com/robots.txt
200          # before robots.txt existed: also the SPA shell
```

A visitor sees a well-designed 404 page. A crawler is told the page exists
and indexes it. That is a "soft 404": Google eventually detects some of them
heuristically, reports them in Search Console, and in the meantime the junk
URLs compete with real pages.

## Why it is not fixable in this repo

The frontend is static files behind nginx. The rewrite that makes client-side
routing work is the same rewrite that produces the 200:

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

`try_files` falls back to `/index.html` and serves it with that file's own
status — 200. React Router then decides, in the browser, that nothing matched.
By the time the app knows it is a 404, the status line has long since been
sent. No amount of frontend code can change it.

`public/robots.txt` and `public/sitemap.xml` are now real files, so they stop
falling through this rule and serve correctly. The 404 status itself still
needs the server config below.

## The server-side fix

On the box serving the frontend, in the site's nginx vhost. The app shell is
served from a named location that carries a 404 status for paths the router
will not match, while real assets keep their normal 200:

```nginx
# Real files and build assets: unchanged.
location /assets/ {
    try_files $uri =404;
    expires 1y;
    add_header Cache-Control "public, immutable";
}

# Everything else: serve the shell, but pick the status based on whether
# the path is one the router actually has a route for.
location / {
    try_files $uri $uri/ @shell;
}

location @shell {
    # Paths the SPA genuinely owns. Keep in step with src/components/App.jsx.
    if ($uri ~ ^/(courses|blogs|current-affairs|forum|explore|counselling|admission|skill|scholarship|quiz|live|about|contact|faq|feedback|terms|privacy|general-studies|become-faculty|become-expert|login|register|dashboard|profile|enroll|payment|moderator|experts|pick-profile|manage-profiles|form-fillup|verify-email|email-verified|resend-verification|forgot-password|signup|vision|mission|values|why-shiksha|privacy-policy|expert-apply|skill-development|upcoming|become-a-teacher|faculty)(/|$)) {
        add_header Cache-Control "no-store";
        try_files /index.html =404;
    }
    # Anything else is not a route: same HTML, 404 status.
    add_header Cache-Control "no-store";
    error_page 404 /index.html;
    return 404;
}
```

### Before applying this

The prefix list above is a maintenance burden and will drift from
`App.jsx`. Two alternatives worth weighing first:

1. **Prerender at build time.** A prerenderer (`vite-plugin-prerender`,
   `react-snap`, or a small Puppeteer script over the sitemap) emits a real
   HTML file per route. Unknown paths then genuinely do not exist on disk and
   `try_files $uri $uri/ =404` gives a correct 404 with no prefix list. This
   also fixes the *other* half of the SEO problem that no amount of nginx
   config touches: link previews. WhatsApp, Facebook and Slack never run the
   bundle, so today every shared URL previews as the generic site card from
   `index.html`. Prerendering gives each page its own.

2. **Server-side rendering.** Correct, and much larger. Not worth it purely
   for this.

Option 1 is the recommended path: it solves soft-404s and per-URL link
previews together, and it deletes the prefix list rather than adding one.

## Verifying the fix

```bash
for u in / /courses /blogs/class-9/science/chapter-7 /nope /robots.txt /sitemap.xml; do
  printf "%-42s " "$u"
  curl -s -o /dev/null -w "%{http_code}\n" "https://shikshacom.com$u"
done
```

Expected after the change: `200 200 200 404 200 200`.

Until then, `src/components/NotFound.jsx` renders `<meta name="robots"
content="noindex,follow">`, which keeps 404s out of the index for crawlers
that execute JavaScript (Google does). It does nothing for crawlers that do
not, which is why it is a stopgap and not the fix.
